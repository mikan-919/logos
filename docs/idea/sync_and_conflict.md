# 同期とConflict

EventベースのLogosでは、ある変化が外部サービスへ伝播し、その結果のWebhookがまた戻ってくることで**無限ループ**が起きうる。さらに外部Interfaceの組み合わせは予測できないため、「お行儀の良い実装」に頼った対策は構造的に破綻する。

ここではループを構造的に断ち、同時に「本物の対立」を取りこぼさない仕組みを定義する。

## 前提: Eventはペイロードを運ばない

Eventは「変化の中身（diff）」を運ぶのではなく、**「このEntityを見直せ」という合図**に過ぎない。

```
Github で title が変わった
  → Event { entity: "Fix Login Bug", reason: "github changed" }   ← 合図だけ
  → System が起動し、両Componentの「現在値」を読み直す
  → 差分があれば揃える、なければ何もしない（no-op）
```

Systemが参照するのはEventの中身ではなく、**Componentの現在の実値**である。これにより、同期は「変化を転送する」行為ではなく「接地したComponent同士の整合を保つ」収束（reconciliation）になる。Logosの哲学（接地）とも一致する。

## ループは「燃料切れ」で止まる

収束モデルでは、書き込みが発生しなければ次のWebhookも飛ばない。

```
Github.title = "B"
Linear.title = "B"   ← さっき揃えた
→ 差分なし → 何もしない → 次のEventは発生しない
```

echo（自分の書き込みが原因で戻ってくるWebhook）は、reconcileした時点で既に値が一致しているため **no-op となり自然消滅する**。ループを能動的に検出して止めるのではなく、冪等性によって勝手に止まる。

## 正規形での比較（必須）

ただし、書いた値が外部ストレージ側で変形されて戻ると（例: `"B"` を書いたが小文字化されて `"b"` で保存）、reconcileが毎回「まだ違う」と判断して上書きし続け、止まらない。

これを防ぐため、Component同士の比較は **生の値ではなく正規化した値（canonical form）**で行う。`"B"` と `"b"` を同値とみなせれば差分は出ず、ループは止まる。

正規形は権威モデルの有無に関わらず常に必要。権威は「上書きの向き」を決めるだけで、「書いた値がstickするか」は保証しないため。

## 順番で解ける対立 / 解けない対立

正規形で畳めない食い違い（例: `"Fix login bug"` vs `"Fix logout bug"`）は、2つの変化の**因果関係**で扱いが分かれる。

- **因果順序がある（happened-before）** — 一方が他方を知った上で起きた変化。echoもこの特殊ケース（自分が原因の、因果的に後の変化）。→ 下流が勝つ／no-op で**自動解決**してよい。
- **並行（concurrent）** — 互いを知らずに同時に起きた変化。どちらが先かは時計のブレでしかなく順番に意味がない。→ これが**本物のConflict**。

本質的なプリミティブは「タイムスタンプの順番」ではなく「因果」である。タイムスタンプは因果の近似に過ぎず、並行ケースでは「たまたま遅かった方」で黙って潰してしまう。

## 並行Conflictの判定

外部サービスはversion vectorをくれないため、Logos側がComponentごとに「最後に書いた値／最後に見た値」を覚えておく。

```
incoming == 最後に書いた値                       → echo（因果的後続）→ no-op
incoming != 最後に見た値
   かつ 相手側にも未反映の変更あり               → 並行 = Conflict
   かつ 相手側に未反映の変更なし                 → ただの新しい編集 → 受け入れて同期
```

echoは収束モデルが自然に吸収する（reconcileすれば既に一致 → no-op）。判別が必要なのは **「両側に未消化の変更があるか」** だけで、それが真の並行衝突を示す。

## Conflictはユーザーに確認させる

並行Conflictは機械的に解決せず、**ユーザーに確認させる**。

これはMergeの哲学と同じ筋である — Mergeは「同じ概念だ」という人間の宣言であり、衝突したら失敗して人間に返す。同じEntityに接地したComponent同士の対立も、黙って片方を上書きで消すのではなく人間に返す。情報を失わないことを優先する。

並行Conflictは稀（同一フィールドを別サービスでほぼ同時に編集した場合のみ）なので、確認の負荷は許容できる。

## まとめ

| 状況 | 止まる/解決するか | 対処 |
|------|------|------|
| echo（不動点あり） | 自然に止まる | 収束モデル（ペイロード非伝播） |
| 変換が非冪等（擬似ループ） | 止まらない | 正規形で比較 |
| 因果順序のある対立 | 自動解決 | 下流が勝つ／no-op |
| 並行Conflict | 止まらない | ユーザーに確認させる（Merge哲学） |
| 外部が正当に編集し続ける | 止まらないが正常 | reconcileが実際の同期を行う |
