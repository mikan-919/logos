# ADR: 設計(b)採用 — Logos をワールドとして持つ

## ステータス

採用済み

## 背景

Logos の設計には2つの選択肢があった。

- **(a)** 各レイヤーが自前 DB を持ち、Logos は参照と書き込みルーティングの層
- **(b)** Logos が Entity/Component ストアを持ち、各レイヤーは「Component 型を定義し、ビューとロジックを提供する Interface（= System）」

当初のドキュメント群は (a) 寄りの前提で書かれていた（"データは各サービスに分散したまま"）。
ただしあの記述は外部サービスとの接地を念頭に置いたもので、自前レイヤーに分散を強制する根拠はなかった。

## 問題

設計 (a) では sync/conflict/reconciliation がコア全体の問題になり、設計が汚染される。
また System（振る舞いの担い手）が概念として不在で、ECS の三位一体が欠けていた。

## 決定

**設計 (b) を採用する。**

Logos = ワールド（ストア + クエリ + 変更通知）。各レイヤー = System。

## 理由

- コア内の Conflict が消える（コピーが存在しない）
- Conflict 問題が外部境界にのみ局所化される
- System = レイヤーという対称な構造になる
- append-only 変更ログで Split を後日いつでも実装できる

## 影響

- Velt/Rotax/Wayline/Yatra/Zestium はすべて System として実装される
- "データは各サービスに分散" は外部サービス向けの記述のみに限定される
- `sync_and_conflict.md` / `event_flow.md` の内容は外部境界（[external_boundary.md](../external_boundary.md)）に移動
