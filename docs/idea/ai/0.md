# ADR: 接地対象としてのEntityと、一覧系ビューの扱い

## ステータス

採用済み

## 背景

GitHub Issue や Linear Issue のような外部対象を同じ概念として統合したい。
中心にあるのは「記号が接地する対象」を扱うこと。
Repository のような複数 Entity をまとめる見方も扱いたいが、Relation を第一級にはしたくない。

## 問題

1. Entity を「何」と定義するかが曖昧だった
2. 複数 Entity をまとめる箱を Entity にするか Component にするかが曖昧だった
3. 「Open issues」のような一覧は実体か見方かが曖昧だった
4. Relation モデル中心は記号接地の思想とずれる懸念

## 決定

Entity は「接地されているもの」— 記号が接地する先。
複数 Entity をまとめて指し示す対象も Entity になり得るが、Group を独立導入せず Component が複数の接地先を持つ形で表す。
一覧・検索条件・抽出結果のような「見方」は Entity にしない（Adapter の責務）。

## 理由

Repository は GitHub 上で独立した対象であり Issue 集合の属性ではない → Entity として接地する方が自然。
Open Issues / Assigned to Me は「見方」に近く Entity 化するとコアが膨らむ → Adapter（レイヤー）のビューとして扱う。

## 採用しない案

- Relation モデル中心: 接地された対象が副次的になり思想とずれる
- Entity の集合を Group 化: 再帰構造・同一性問題を増やす

## 影響

| 要素 | 責務 |
|------|------|
| Entity | 接地される対象 |
| Component | Entity に属する表現 |
| Adapter（外部レイヤー） | 外部対象・見方を内部表現へ変換 |
| View / 一覧系 | Adapter（レイヤー）の責務 |

> 「Adapter」は新方針の「外部サービスのレイヤー（System）」に相当。[layers.md](../layers.md) 参照。

## 未解決点

1. 複数 Entity を指す Component の具体的な型表現
2. Entity と「見方」の境界をどこまで厳密に切るか
3. Repository のような実体と検索結果としての集合を同じ抽象で扱う程度
