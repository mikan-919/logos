# ADR: 接地対象としてのEntityと、一覧系ビューの扱い

## ステータス

提案中

## 背景

Logosでは、GitHub IssueやLinear Issueのような外部サービス上の対象を、同じ概念として統合したい。ここで中心にあるのは、単なるデータではなく「記号が接地する対象」を扱うこと。さらに、Repositoryのように複数のEntityをまとめて見る見方も扱いたいが、それをRelationとして第一級に置くのは避けたい。

## 問題

1. Entityを「何」と定義するかが曖昧だった。
2. 複数Entityをまとめる箱を、Entityとして持つべきか、Componentとして持つべきかが曖昧だった。
3. GitHubの「Open issues」のような一覧は、実体なのか見方なのかが曖昧だった。
4. Relationモデルを中心にすると、記号接地の思想からずれる懸念があった。

## 決定

Entityは「物そのもの」ではなく、「接地されているもの」とする。より正確には、外部表現が指し示す対象、すなわち記号が接地する先を Entity とみなす。

このとき、Entity は単体の対象に限らず、複数の Entity をまとめて指し示す対象にもなり得る。ただし、その「まとめるもの」を新しい Group として独立に導入するのではなく、あくまでその Component が指し示す先として複数 Entity を許す。再帰的な Group 構造は前提にしない。

一方で、単なる一覧・検索条件・抽出結果のような「見方」は Entity にしない。これらは Adapter 側の責務として扱う。

## 理由

Repository のようなものは、単に Issue の集合として扱うと不自然になることがある。Repository 自体は GitHub 上で独立した対象として扱われ、Issue 集合の属性ではないからである。したがって、Repository は Entity として接地させる方が自然である。

逆に、Open Issues や Assigned to Me のようなものは、対象そのものではなく対象の見方に近い。これらを Entity 化すると、境界が曖昧になり、コアモデルが不必要に膨らむ。よって Adapter のビューとして扱う方がよい。

## 採用しない案

単純な Relation モデルを中心にする案は採用しない。理由は、関係を主役にすると「接地された対象」が副次的になり、Logosの思想とずれるためである。

また、Entityの集合を独立した Group として一般化する案も採用しない。これは表現力は高いが、再帰構造や同一性問題を新たに増やすためである。

## 影響

この決定により、Logos のコアは次のように整理される。

* Entity: 接地される対象
* Component: Entity に属する表現
* Adapter: 外部サービス上の対象や、その見方を内部表現へ変換するもの
* View / 一覧系: Adapter の責務

## 未解決点

1. 複数Entityを指す Component の具体的な型表現をどうするか。
2. Entity と「見方」の境界をどこまで厳密に切るか。
3. Repository のような実体と、検索結果としての集合を、どの程度まで同じ抽象で扱うか。

## ひとまずのまとめ

Logosでは、Entity を「接地されているもの」と定義する。複数Entityをまとめる表現はあり得るが、それを一般的な Group 構造として拡張するのではなく、Component が複数の接地先を持つ形で表す。単なる一覧や検索条件は Entity 化せず、Adapter の見方として扱う。
