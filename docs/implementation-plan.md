# Logos — 機能の組み合わせから育つワークスペースの実装計画

作成日: 2026-09-07 / v0.1 提案

## 1. 目指すもの

持続的な対象に機能上の側面を追加でき、その組み合わせに応じて、利用できる操作と画面が増えるワークスペースを作る。

Entityは対象の同一性、Componentは意味の定まった状態を担う。操作と画面はその状態を利用する。一つの対象を文書、一覧、カレンダーから扱っても、同じID・状態・履歴が維持される。

今回の会話で確認できた意図は、持続的な対象を中心にすること、Entity／Componentの構成を借りること、機能上の側面が見た目に反映されること。それ以外の具体的なモデル、機能、工程は、この計画での提案である。

最初に確かめる仮説は二つ。

- 技術: 対象を作り直さずに機能を追加し、複数の画面から矛盾なく操作できる。
- 利用価値: 機能を組み合わせる負担より、情報を作り直したり転記したりせずに済む利益が大きい。

引き継ぎ支援やAI記憶の需要検証を、この試作の前提条件にはしない。AIや外部サービスは将来、この持続的な対象に触れる入口となる。

## 2. 最初の完成体験

「勉強会を開催する」という一つの活動を、次の順に扱えるようにする。

1. 名前と本文だけで作成し、目的や内容を書く。
2. 「進捗を管理」を選ぶと、その場で未着手・進行中・完了を扱えるようになる。
3. 「実施予定を追加」を選び、開始・終了日時を設定する。
4. カレンダーに同じ活動が現れる。予定を変更すると詳細画面にも反映される。
5. 完了にしても、本文、予定、対象ID、変更履歴が残る。
6. 実施予定を外すとカレンダーの対象から外れるが、活動そのものは残る。予定は復元できる。
7. 後から見積時間の機能を追加し、既存の活動にそのまま適用できる。

この対象から生まれた「会場を予約する」という別の作業は、別Entityを作って関連付ける。同じ話題に関係するという理由で、すべてを同じEntityに集めない。

成功デモでは、サンプルに加えて空のワークスペースから作成する。同じ操作を「記事を書く」でも行い、勉強会専用の実装になっていないことを確認する。

## 3. 最初に固定するモデル

| 要素 | 役割 | 初期ルール |
| --- | --- | --- |
| Entity | 持続的な対象 | ID、名前、作成日時、revision、アーカイブ状態。IDは再利用しない |
| Component | 対象に属する機能上の状態 | 型ID、スキーマ版、データ。有効な同種Componentは一つまで |
| Command | 意味のある操作 | 入力、必要なComponent、検証、更新範囲を宣言する |
| Projection | 状態を読み、操作を提示する画面 | 適用条件で対象を選び、更新は共通Commandを呼ぶ |
| Relation | 独立した対象間の関係 | 初期はreferencesのみ。作成操作と作成者を記録する |
| Feature module | 開発者が追加する機能の単位 | Component定義、Command、画面部品、必要ならProjectionを登録する |

Entityの名前は一覧や参照に必要な最小メタデータとして扱う。画面の利用条件を、固定的な「Task型」「Note型」には依存させない。初期テンプレートはComponentと初期値の組み合わせであり、別の保存形式を作らない。

Componentには状態を保存し、実行コードやUI定義そのものをデータとして混ぜない。Feature moduleが必要な実装をまとめて登録する。初期は同梱されたコードだけを使い、第三者コードの動的実行やマーケットプレイスは扱わない。

### 最初の三つのComponent

| Component | データ | 意味と操作 |
| --- | --- | --- |
| Body | Markdown文字列 | 対象そのものの説明。編集・プレビューできる |
| Progress | todo / doing / done | 利用者が明示的に変更する。期限や時計から自動変更しない |
| Schedule | 開始、終了、タイムゾーン | 一回の実施予定。締め切りとは別の意味にする |

Scheduleの初期仕様は時刻付きの単発予定。開始より終了が後であることを検証する。UTC時刻とタイムゾーンを保持し、表示時に変換する。終日予定、繰り返し、複数の作業枠は、まず対象外としてUIにも明示する。

同じ対象に複数の議事録や複数の実施回が必要なら、それらは独立したEntityを関連付ける。これは初期の制約であり、将来の複数Componentや役割付きスロットを否定するものではない。

### ComponentとEntityを分ける判断

そのデータが対象の説明・状態であり、対象と一緒に扱うならComponentを候補にする。個別に参照、共有、完了、版管理したいなら別Entityを候補にする。判断が分かれる例を設計記録に残す。

例: 活動の説明はBody。独立した議事録はDocument相当の別Entity。活動の実施日時はSchedule。活動から派生した宿題は別Entity。リンクを使うこと自体は失敗ではなく、対象の境界を保つために必要な操作とする。

## 4. 操作と表示の契約

最初の画面は、対象一覧、対象詳細、週カレンダーの三つ。

- 一覧は全対象を扱い、Progressの有無や状態で絞り込める。
- 詳細は有効なComponentの編集部品を組み合わせる。機能追加は「進捗を管理」「実施予定を追加」など、結果が分かる名前で提示する。
- カレンダーはScheduleを持つ対象を扱う。Progressがあれば状態も表示し、なくても予定として操作できる。

カレンダーの最初の日時変更はフォーム操作でよい。ドラッグ操作は同じCommandを呼ぶ追加UIとして、体験が成立した後に実装する。

必要なCommandは、対象作成・改名・アーカイブ・復元、機能追加・解除・復元、本文編集、進捗変更、実施予定の設定・変更、参照追加・解除とする。

一つの操作は一つのトランザクションにする。例えば機能追加と初期値設定が途中で分離しないようにする。画面からComponentの値を直接保存する別経路は作らない。

各画面は同じ対象IDを使う。独自の「カレンダー予定」「一覧行」の正本は作らない。表示用のキャッシュは再取得できる派生データとする。

複数画面の古い情報による上書きを防ぐため、更新にはexpectedRevisionを付ける。不一致なら保存せず、最新状態と入力内容を示して再適用させる。初期はEntity単位の粗い競合検出でよい。

UIが「保存済み」と表示するのは永続化が成功した後。別画面は通知で再取得し、再接続・画面復帰時にも取得する。楽観的な表示は失敗時に訂正できることを条件にする。

### 組み合わせのルール

- 三つのComponentの有無による8通りを扱う。Componentがない状態は不完全なエラーではない。
- 名前だけの対象も一覧と詳細から開ける。
- 日時経過から完了、完了から予定削除といった暗黙の連動は行わない。
- 機能解除は論理的な解除とし、最後のデータと履歴を保持する。復元時は保存済みデータを使う。
- Projectionを非表示にしても、機能やデータは解除しない。
- 不明なComponent型は削除・解釈せず保持し、読み取り専用の代替表示を出す。
- 将来、Component間の依存が必要になったら明示的に宣言する。組み合わせの意味をUIごとの条件分岐に散らさない。

## 5. 実装構成と保存

既存のTypeScript資産を活かし、ローカルで動く単一プロセスのアプリとブラウザーUIを初期構成にする。UIライブラリの選定は現行画面の再利用性を確認した後に行い、製品仮説には含めない。

依存方向は、UI／将来のMCP → 共通Command・Query → Component定義と検証 → 永続化、とする。Kernelは具体的なカレンダーやエディタを知らない。

試作の保存にはSQLiteを推奨する。現在状態と追記式の変更イベントを同一トランザクションで保存し、状態だけ、履歴だけが更新されることを防ぐ。SQLiteのトランザクションは変更の全適用または全取消を提供する。[SQLite公式資料](https://sqlite.org/transactional.html)

表の候補はentities、components、relations、events。Componentのデータは型別に検証したJSON、型IDとスキーマ版は明示カラムで保持する。履歴には対象ID、操作ID、更新前後のrevision、変更内容、実行者、時刻を記録する。

現在状態は通常の読み取り用、イベントは変更履歴と再構築用とする。過去イベントを削除・再実行して巻き戻す方式ではなく、復元も新しい操作として記録する。イベント形式に版を付け、将来の変更に備えた再構築テストを用意する。

同じ操作の再送はoperationIdで識別し、二重適用しない。初期の所有者は一人、書き込み入口はローカルサーバーに集約する。ローカル接続の検証を入れ、チーム権限や遠隔公開は別工程にする。

初期のQueryはComponentの有無、状態、日時範囲、名前検索、ID参照で十分。汎用クエリ言語、専用グラフDB、ゲーム向けECSの高速メモリ配置は初期要件に含めない。ECSから借りる中心は、IDと構成可能な状態の分離である。[Flecs公式資料](https://www.flecs.dev/flecs/md_docs_2EntitiesComponents.html)

## 6. 現行MVPとの関係

2026-09-07にGitHub上のmikan-919/logosのmainを確認した。HEADは引き継ぎメモと同じ06a5056a5382c92d814762d53bbc4d90626a6264。README、CONCEPT、ROADMAP、docs/MVP、types、event-store、mcpとkernel冒頭を読んだ。今回は実装変更とテスト実行を行っていない。

現行Componentはkindと任意データ、provider、externalIdなどを持つ。機能ごとのスキーマと操作契約は、確認した定義にはない。現行Entityは開発領域の固定種別を持つ。MCPは三つのRead／Explain／Propose系ツールで、保存は.logos/events.jsonlである。[現行types.ts](https://github.com/mikan-919/logos/blob/06a5056a5382c92d814762d53bbc4d90626a6264/src/types.ts)、[現行README](https://github.com/mikan-919/logos/blob/06a5056a5382c92d814762d53bbc4d90626a6264/README.md)

今回の構想は現行の「開発プロジェクト向けSemantic Context MVP」と優先順位が異なる。旧ROADMAPの需要検証を今回の着手条件に流用しない。

| 現行資産 | 今回の扱い |
| --- | --- |
| 安定ID、履歴、検証の考え方 | 継承候補。実装の再利用範囲は既存テストと合わせて調査 |
| append-only保存 | 追記履歴の原則を継承。新試作のトランザクション保存は別実装 |
| Component型 | Functional Componentを別定義。旧kind／providerを機械的に置き換えない |
| 外部表現、Evidence、Hypothesis | 旧機能として保持。将来の外部接続層の候補 |
| CLI／HTTP／MCPの境界 | 既存利用を保ち、新試作は専用入口から動かす |
| ダッシュボード | スタイルなどの再利用は検討。意味関係レビュー画面を主UIにしない |

実装開始時は、分離した試作ディレクトリと専用データファイルを設ける。旧.logos/events.jsonlは自動移行しない。最初は新規データで設計を検証する。

基盤への統合は、拡張実験の完了後に判断する。統合する場合は旧データのコピーを入力とし、ID、外部識別子、根拠、履歴、不明なデータを保つ変換と照合を別タスクにする。旧MCPを黙って書き込み可能にしない。

## 7. 実装順序と完了条件

工数は専任開発者一人、ローカル試作を想定した仮置き。依存環境と既存コードの調査後に更新する。実装は概ね12〜20作業日、利用観察は別途2週間を目安とし、製品公開までの見積もりではない。

| 工程 | 工数目安 | 作るもの | 次へ進む条件 |
| --- | --- | --- | --- |
| 0. 意味と境界の具体化 | 1〜2日 | モデル定義、Command契約、勉強会／記事／宿題の例、既存コード再利用表 | 同じEntityか別Entityか、予定と締め切りの違いを具体例で説明できる |
| 1. 最小の操作と保存 | 3〜5日 | Entity、三つのComponent、検証、共通Command、履歴、再起動復元、粗い入力画面 | 本文と予定を一つの対象に保存・変更でき、再起動しても残る |
| 2. 複数画面での一貫性 | 4〜6日 | 一覧、詳細、週カレンダー、機能追加／解除、競合表示、Relation | 空の状態から完成体験の1〜6を実行し、全画面で同じ状態になる |
| 3. 拡張性の実験 | 2〜3日 | 四つ目のEstimate Componentと見積時間一覧、登録方法の短い資料 | Kernel、保存構造、既存Componentを変更せず、登録と新機能実装で追加できる |
| 4. 日常利用の準備 | 2〜4日 | エラー表示、履歴閲覧、エクスポート／復元、サンプル、導入説明 | 自分の実データで使え、バックアップからID・状態・履歴を復元できる |
| 5. 利用観察 | 2週間 | 本人と3〜5人の利用記録、既存手段との比較 | 他者が自分の対象に繰り返し使い、手間の削減を具体例で示せる |

工程1でも簡単な入力画面を用意し、Kernelだけを長期間作り込まない。工程3の「Kernelを変更しない」は機能ごとの特例が不要という意味で、登録箇所への追加や新しい画面実装は含めてよい。

工程3で大きな変更が必要なら、プラグイン基盤を増築する前に、責務の分離を修正する。工程5は参加者の協力が必要であり、募集や連絡はこの計画の作成では実行していない。

## 8. 検証項目

テストは構想が壊れやすい境界を中心にする。

- 三つのComponentの8通りで、対象の可視性と利用可能な操作が正しい。
- 機能追加前後、画面変更前後、再起動前後で対象IDが変わらない。
- 同じ機能を二重追加しても有効な同種Componentが増えない。
- 予定変更は本文と進捗を変えず、進捗変更は予定を消さない。
- 無効な予定は保存も履歴追加もされない。
- 二つの画面から同じrevisionを更新すると、後の更新が古い状態で上書きしない。
- 操作途中の失敗で、現在状態と履歴の片方だけが残らない。
- 再送で二重更新が起きず、機能解除と復元で値を失わない。
- エクスポートから復元した状態と履歴、イベントから再構築した状態を照合できる。
- 未知のComponentを含むデータでも、それを保持したまま既知の機能を読める。
- UIからの一連の操作が共通Commandを経由し、別画面に反映される。
- 四つ目の機能追加によって、既存三機能の意味が変わらない。

機能解除の復元や履歴閲覧は初期範囲だが、任意の過去時点への全体巻き戻し、全操作の汎用Undoは追加工程とする。

## 9. 使う理由の検証

対象候補は、同じ活動について説明を書き、予定を立て、進捗も管理する人。職種だけで決めず、本人の実際の扱い方を見る。

比較相手は、その人が使っているノート、表、タスク管理、カレンダーの組み合わせ。既存ツールで十分簡単にできる場合も、そのまま記録する。

見る項目は、同じ内容の再入力・転記・訂正、対象への機能追加にかかる手間、意図しない連動、元の情報を探す回数、次の活動への自発的な利用。

初回デモの反応より、本人が新しく作った対象に二つ目・三つ目の機能を付けるかを見る。「追加された見方が便利」だけでなく、同じ対象を使い続けることが役立ったかを聞く。

暫定の判断基準として、本人以外の少なくとも二人が二週間のうち複数日に自分の活動で再利用し、具体的な再入力や訂正の削減例を示せれば、次の用途への拡張を検討する。これは需要の証明や統計的基準ではなく、開発を続けるための探索的な基準である。

使われなければ、抽象化の正しさで反論せず、機能追加の分かりにくさ、既存手段との差、対象の分け方を確認する。技術的に成立したかと、利用価値が成立したかは別々に記録する。

## 10. 今回の範囲と次の分岐

初期には、一般利用者向けスキーマビルダー、任意レイアウト生成、外部アプリの双方向同期、共同編集、スマートフォン対応、AI推論、広い権限モデル、プラグイン配布基盤を含めない。

MCPは工程3の後に、同じEntity・Component・操作定義を読み取る薄い入口から追加を検討する。AI向けに別の対象モデルを持たせない。書き込みを追加する場合も、通常UIと同じCommandと検証を通し、許可する操作を別途定義する。

利用価値が出た後は、実際に必要になった方向を一つ選ぶ。複数予定や締め切り、独立した文書、既存データの移行、外部接続、別のProjectionなどから選び、用途を増やすたびに基盤そのものを作り直していないかを確認する。

最初の着手項目は、工程0のモデルと操作契約を短く確定し、工程1の「一つの対象に本文と予定を持たせ、変更して、再起動後も読める」までを動かすこと。
