# ワークスペース利用観察の手順と記録様式

作成日: 2026-09-08
状態: 準備完了、観察未開始

## 目的

工程5では、ワークスペースを実際の活動で繰り返し使い、既存手段との差を記録する。この文書は、観察の条件、記録する項目、判定方法を固定する。実装の完成度と利用価値を別に記録する。

工程0〜4の実装、試験、バックアップ手順は完了している。工程5にこの文書を追加するだけで、UIや保存形式は変更しない。参加者への連絡、利用の実施、結果の記入はこの変更の範囲に含めない。

## 範囲

### 含むもの

- 本人と、本人以外の3〜5人を候補にした利用観察。判定に必要なのは本人以外の2人以上とする。
- 二週間を観察期間とし、各参加者が自分の活動を複数日に繰り返し扱う記録。
- 参加者が現在使っているノート、表、タスク管理、カレンダーなどとの比較。
- 同じ対象に本文、進捗、実施予定、見積時間、参照を追加・変更する過程の記録。実際に必要になった機能だけを使う。
- 対象ID、履歴、エクスポートを使った技術上の事実の確認。

### 含まないもの

- 新しいComponent、画面、同期、権限、分析機能の追加。
- 参加者への連絡、募集、同意取得の実行。
- 参加者に機能の組み合わせを強制すること、既存手段との二重入力を強制すること。
- 統計的な効果の主張や製品公開の判断。
- 本文、個人名、連絡先などの生データをGit管理下へ保存すること。

## 準備

1. 参加者コードを`P01`、`P02`のように割り当て、氏名や連絡先を記録ファイルへ書かない。
2. 参加者ごとに観察用の作業ディレクトリを用意する。サーバーはリポジトリの絶対パスから起動し、作業ディレクトリを保存先にする。

   ```console
   cd /path/to/observation/P01
   bun run /absolute/path/to/logos/src/workspace/cli.ts serve --port 4318
   ```

   `process.cwd()`（プロセスの現在ディレクトリ）が`.logos-workspace/workspace.sqlite`の基準になる。既存の`.logos/events.jsonl`は読まない。生成されたSQLiteファイルはGitへ追加しない。
3. 観察開始前に、使用するLogosのコミット、開始日時、比較する既存手段を記録する。
4. エクスポートや画面の記録を残す場合は、参加者の同意と保存期間を確認する。生データはリポジトリ外へ置き、記録ファイルには保存場所と生成日時だけを書く。必要な場合はSHA-256（ファイル内容の改変を検知する暗号学的要約）を記録する。

## 観察手順

各参加者について、次の順で行う。活動の内容や機能の選択は参加者に任せる。

1. 現在の手段で、同種の活動を作成、更新、確認する方法を聞く。再入力、転記、訂正、情報を探す場所を記録する。既存手段が十分な場合もそのまま記録する。
2. Logosで参加者自身の活動を一件作成し、必要な機能だけを追加する。対象詳細、対象一覧、週カレンダー、見積時間一覧を使った場合は記録する。
3. 別の日に同じ対象を開き、本文、進捗、予定、見積時間、参照のいずれかを更新する。対象IDと変更履歴が維持されたかを確認する。
4. 複数日に新しい活動を作るか既存の活動を再利用する。少なくとも二つの活動、複数日の利用、機能追加後の再利用を目標にする。参加者が続けない場合は、その理由を記録して終了する。
5. 観察期間の最後に、既存手段と比べて減った作業、増えた作業、分かりにくかった操作、使わなかった機能を聞く。
6. 必要な場合だけエクスポートを取得する。エクスポートの`entities`、`components`、`relations`、`events`を確認し、観察記録には個人データを転記しない。

## 記録様式

この文書を複製して観察記録を作る。未記入の項目を推測で埋めない。「未確認」「該当なし」「中止」を使い分ける。

| 観察期間 | `YYYY-MM-DD`〜`YYYY-MM-DD` |
| 実施者 |  |

| 保存したエクスポート | リポジトリ外の場所、または「なし」 |

### 参加者一覧

| 参加者コード | 区分（本人／本人以外） | 活動の種類 | 既存手段 | 利用日数 | 継続利用 | 具体的な削減例 | 状態 |
| --- | --- | --- | --- | ---: | --- | --- | --- |

区分、活動の種類、既存手段は個人を特定できない範囲で記録する。利用日数は実際に操作した日数とし、ログイン日数とは分ける。

### セッション記録

一行を一回の利用として記録する。

| セッションID | 参加者コード | 日付 | 対象の説明 | 操作と利用画面 | 既存手段での作業 | 再入力・転記 | 訂正 | 情報を探した回数 | 意図しない連動 | 結果と発言 | 証拠への参照 |
| --- | --- | --- | --- | --- | --- | ---: | ---: | ---: | --- | --- | --- |
| S001 | P01 | `YYYY-MM-DD` |  |  |  |  |  |  |  |  |  |

数値を測れない場合は「未確認」と書く。発言は個人を特定できない要約にする。証拠への参照はエクスポートのファイル名、対象ID、履歴の操作名などに限定し、生データを貼り付けない。

### 指標の定義

- 再入力・転記: 同じ内容を別の画面または既存手段へ手で入力した回数。
- 訂正: 複数の場所の状態が一致せず、内容を合わせ直した回数。
- 情報を探した回数: 対象の現在状態や予定を確認するために開いた場所の数。移動回数を測れない場合は「未確認」とする。
- 機能追加の手間: 「機能を追加」から保存済みになるまでの時間または参加者の評価。測定方法を併記する。
- 意図しない連動: 一つのComponentの操作で、利用者が意図していない別ComponentやEntityが変わった事実。発生しなければ「なし」と書く。
- 継続利用: 観察者の依頼ではなく、参加者が別の日に自分の活動で再び使ったこと。

| 参加者コード | 使い続けた理由 | 使わなかった理由 | 減った作業の具体例 | 増えた作業の具体例 | 分かりにくかった操作 | 次に必要な変更（あれば） |
| --- | --- | --- | --- | --- | --- | --- |
| P01 |  |  |  |  |  |  |

「次に必要な変更」は観察終了後に記録する。観察中にコードを変更しない。

## 判定

### 技術上の確認

次を事実で確認する。既存の自動試験で確認済みの項目は試験名を参照し、観察で再確認した項目だけを記録する。

- 同じ対象を別の日に開いたとき、対象IDと状態が維持された。
- 追加・変更した機能が対象詳細、一覧、週カレンダー、見積時間一覧の表示に反映された。
- 不要な機能を使わなくても対象を作成・更新できた。
- 操作の失敗、競合、再接続があった場合の状態と履歴を確認した。

### 利用価値の判定

計画本文の暫定基準をそのまま使う。

- 本人以外の少なくとも2人が対象を自分の活動に使った。
- その2人が二週間のうち複数日に再利用した。
- それぞれが再入力、転記、訂正、情報を探す作業の削減を具体例で示した。

三つを満たした場合だけ「次の用途への拡張を検討」と記録する。満たさない場合は、抽象化の正しさを根拠に反論せず、機能追加の分かりにくさ、既存手段との差、対象の分け方のどれを確認するかを次の作業にする。これは需要の証明や統計的基準ではない。
