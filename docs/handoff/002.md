# Handoff: Logosの「最初の一歩」に関する対話（002）

## このドキュメントの目的
`handoff/001.md`（設計方針：Logos=ワールド、レイヤー=Systemという(b)案の採用）を受けた次の対話のまとめ。001の方針が「コアを薄くする」ことに振れすぎて、結果としてLogosの存在価値そのものが見えなくなるのではないか、という疑問から始まり、価値の正体と、実装として最初に何を作るべきかを具体化した。

## 出発点：001の整理が生んだ新たな不安
001で「Logos = Entity/Componentストア＋クエリ＋変更通知だけのワールド」と整理した結果、それを単体で見ると汎用ECSストア／自作DBラッパーと区別がつかなくなり、「これはプロダクトとして何が独自なのか」という空虚感が生まれた。これは整理そのものの誤りではなく、価値を全部System（レイヤー）側に押し出した副作用として価値が見えなくなっただけ、という点を確認した。

## Logosの本質的価値の再定義
ワールド機能（ストア・クエリ・通知）自体には独自性がない。本当に他で代替できない価値は次の三つの「宣言」に集約される。第一に同一性の宣言（Merge）——「このRotaxタスクとこのVeltノートとこのGitHub Issueは同じ概念だ」という事実は、現状どのツールのDBにも存在しえず、Logosだけが一次データとして保持できる。第二に由来付きの変更履歴——概念単位で「どのレイヤーから何が変更されたか」が一本のログになるのは、データがツールごとに分断されている限り原理的に不可能。第三に外部境界のreconciliation——`external_boundary.md`の設計（echo消滅・正規形比較・並行Conflict判定）は捨てた知見ではなく、最も模倣されにくい資産として位置づけ直された。つまりLogosの価値は「ストアであること」ではなく「概念の同一性情報を一次データとして持つ唯一の場所であること」であり、ワールド機能はその情報を運用可能にするための器にすぎない。

## 検証課題の具体化
001で示された「RotaxかVeltを最小Systemとして書く」という次アクションを、もう一段具体化した。検証すべきことは「Componentを2つ以上持つEntityが自然に生まれ、それが役に立つ瞬間を最短で1回作る」こと。これが成立すればLogosの価値は実証され、成立しなければ（Entityが常にComponent1個しか持たない＝レイヤーは独立アプリで十分だった、と分かれば）早期に方向転換できる。どちらに転んでも問いに答えが出るという点が重要。

## 最初に作るものの順序
作らないものを先に確定した：Interfaceのプラグイン機構（Bun Worker分離・URL配布）、外部サービスAdapter、Merge UI、Conflict処理、権限、変更通知のpub/sub。これらは「必要になった日」がまだ来ていない。

実装順序は三段階。まず最小のワールドだけを作る——テーブルは`entities(id)`、`components(entity_id, type, data_json)`（`(entity_id, type)`にユニーク制約）、`changes(id, entity_id, component_type, data_json, origin, timestamp)`のappend-onlyログの3つだけ。APIは`createEntity()`, `setComponent()`, `removeComponent()`, `query(types: string[])`, `getChanges(since)`の5関数程度で、`setComponent`が必ず`components`へのupsertと`changes`へのinsertをワンセットで行う（これが001の「書き込みの単一口」と「append-onlyログ」という2つの安い保険の実装そのもの）。次にRotaxの最小版——`RotaxTask {title, status, scheduledAt}`を定義し、`query(["RotaxTask"])`で一覧表示・作成・完了切り替えができるだけのCLIか簡易UI。この段階では「SQLite直結のTodoアプリと何が違うのか」と感じるはずだが、それは正常な状態として想定済み。最後にVeltの最小版とMergeの原始形——`VeltNote {content}`を定義して表示し、「このタスクとこのノートは同じ概念だ」と宣言する操作（ノート側EntityのComponentをタスク側Entityに移すだけの関数）を実装し、Rotaxのタスク詳細画面で同じEntityに乗っているVeltNoteがあれば表示する。ここで初めて「概念への接地」という体験が生まれ、検証課題への答えが出る。

## ORMとappend-onlyログについての補足
ORM導入は前回の「薄く作る」方針と矛盾しない。削るべきとされた「DB Adapter抽象化」「クラウド/self-hosted両対応」は抽象化そのものの話であり、ORM（BunならDrizzle推奨）はその抽象を肩代わりする実装手段なので、最初から使ってよい。Drizzleのスキーマ定義はTypeScriptの型に対応し、`(entity_id, type)`のユニーク制約も型レベルで表現でき、SQLite→Postgresの移行もドライバ差し替えで済む。

append-onlyログ（`changes`テーブル）は「データを上書きせず変更そのものを行として追記し続けるテーブル」のこと。`components`テーブルは現在状態のスナップショットとして上書きされてよいが、`changes`には「entity_id, component_type, data, origin, timestamp」が時系列で残り続ける。これが重要なのは将来のSplit（一度Mergeした2つのEntityを後で分離する操作）のため——由来付きログがあれば「このフィールドの値はどのレイヤー由来の変更か」を遡って再構成でき、Splitを「今すぐ実装する機能」から「必要になった日に過去ログから実装できる後回し可能な機能」にできる。さらにこの構造は001で触れたYatra（活動履歴レイヤー）の土台とほぼ同一なので、二重投資にならない。現時点ではこのログを読む仕組み（クエリAPIやUI）まで作る必要はなく、書くだけで十分。

## 次のアクション
1. Bunプロジェクトを初期化し、Drizzle + SQLiteで`entities`/`components`/`changes`の3テーブルを定義する。
2. `setComponent()`をはじめとする最小ワールドAPI（5関数）を実装し、`components`へのupsertと`changes`へのinsertを同一トランザクションで行う。
3. RotaxTaskの最小CLI/UIを作り、「SQLite直結Todoと同じに見える」状態を一旦受け入れる。
4. VeltNoteとMergeの原始形を実装し、同一Entity上で2つのComponentが共存する体験を1つ作る。

## 未解決・次セッションで詰めるべき論点（001から継続）
- (a)/(b)の最終確定は(b)で方向は合意済みだが、3.のRotax実装を通じて初めてAPIの形が決まる。
- 各レイヤー（Wayline/Zestium/Rotax/Yatra/Velt）が定義するComponent型の初期スケッチは、Rotax/Velt実装時に決める。
- Yatraと「変更ログ（changesテーブル）」の一体設計は、append-onlyログを実装した時点で再検討する。
