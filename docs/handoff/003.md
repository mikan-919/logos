## 実装済みの内容

### スキーマ（`packages/core/src/db/schema.ts`）

3テーブル構成：
- `entities(id, created_at)`
- `components(id, entity_id, type, data JSON, origin, authority, created_at, updated_at)` — `(entity_id, type)` にUNIQUE制約
- `change_log(id, entity_id, component_type, op, data_before, data_after, origin, at)` — append-only

### ワールドAPI（`packages/core/src/world.ts`）

`createWorld(db)` が返す関数：
- `createEntity()` → entity id
- `setComponent(entityId, type, data, origin, authority?)` → upsert + change_logを同一トランザクション
- `removeComponent(entityId, type, origin)`
- `query(types[])` → すべての型を持つentity idの配列
- `getComponents(entityId)` → そのentityの全component
- `getChanges(since: Date)`
- `merge(toId, fromId, origin)` → fromIdの全componentをtoIdへ移動、同型があればエラー

### DB初期化（`packages/core/src/db.ts`）

`createDb(path?)` — `bun:sqlite` + Drizzle。マイグレーションなし、CREATE TABLE IF NOT EXISTSで起動時に自動作成。

### Rotaxパッケージ（`packages/rotax/`）

Component型：
- `Name { title: string, description?: string }`
- `Task { status: "todo" | "done" }`

`createRotax(world)` が返す関数：`createTask`, `listTasks`, `completeTask`, `reopenTask`

### Veltパッケージ（`packages/velt/`）

Component型：
- `VeltNote { content: string }`

`createVelt(world)` が返す関数：`createNote`, `listNotes`

## 検証結果

`packages/rotax/src/try-merge.ts` で以下を確認済み：

1. RotaxタスクEntityとVeltNoteのみのEntityを別々に作成
2. `world.merge(taskId, noteId, "logos")` で統合
3. マージ後のtaskIdに `Name` + `Task` + `VeltNote` の3つのComponentが共存
4. `rotax.listTasks()` からVeltNoteが見える

また、両EntityにNameがある場合のMerge conflictエラーも正常に発生することを確認。

## 設計上の決定事項（このセッションで確定したもの）

- ComponentストアはAアプローチ（1テーブル + JSON data）を採用
- `Name`はtitleとdescriptionを持つ独立Component（Entity自体は名前を持たない）
- `Task`はstatusだけ。scheduledAtはいったんなし
- VeltのcreateNoteはNameなしでも作れる（Nameなしで接地させてからmergeで統合するパターンが自然）
- `packages/rotax/package.json`に`@logos/velt`の依存を追加済み
