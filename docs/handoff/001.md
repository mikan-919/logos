# Handoff: Logos の設計方針に関する対話

## このドキュメントの目的
Logos（概念グラウンディング基盤）の設計について、ユーザーと行った対話の到達点をまとめたもの。次のエージェントがこの続きから設計・実装の相談に乗れるようにする。元のリポジトリ設計ドキュメント（`adr/`, `idea/` 配下）の内容はここでは複製しない — それらを参照しつつ、本対話で更新された「方針の差分」だけを記録する。

## 背景：Logos とは何か
- Logos は ECS（Entity-Component-System）の Entity / Component を応用した、「概念こそが一次的実在で、各サービス上の表現（Issue やノート）はその投影にすぎない」という思想の基盤レイヤー。
- 当初は GitHub Issue / Linear Issue のような**外部サービス統合**を中心ユースケースとして設計されていた（`idea/sync_and_conflict.md`, `idea/event_flow.md` 等）。
- しかし実際の主目的は、ユーザー自身のエコシステム（Wayline / Zestium / Rotax / Yatra / Velt という複数レイヤー）の**共通基盤（背骨）**であることが対話で判明した。Linear は単なる例で、ユーザーはほぼ使っていない。

## 対話で到達した主要な結論

### 1. Logos の「汚さ」の正体
今のドキュメントには二つの別物が一つのモデルに同居している：
- (A) 自分のレイヤー群が共有する**データ基盤**（Entity/Component ストア、レイヤー間参照、書き込みルーティング）— 綺麗にしうる。
- (B) 非協力的な**外部サービスとの接地・同期機構**（Adapter, Event, reconciliation, Conflict 処理）— echo / 正規形 / 並行 Conflict 等の都合がコアを浸食している。

→ **方針：コアは内部レイヤー向けに綺麗に作り、外部接地は「コアの上に乗る一つの応用（reconcile する Bridge）」として外に押し出す。** これで汚さの大半がコアから出ていく。ADR-0001 の Interface 間依存の曖昧さや TaskAssign の衝突は、「外部サービスも内部レイヤーも同じ Interface 抽象で扱おうとした」歪みが原因。

### 2. 欠けていた第三項 = System はレイヤーそのもの
- ユーザーの違和感「ECS の三位一体感が Logos にない」は構造的に正しい。Logos は E と C だけの 2/3 システムで、System（振る舞いの担い手）が実質空席だった。
- **結論：System = Velt / Rotax などのレイヤーそのもの。** RenderSystem が「Position+Sprite を持つ Entity」を走査するのと同様、Rotax は「RotaxTask を持つ Entity」に対するビューとロジック。
- 「Rotax の画面から Velt の内容・優先度を書き換える」は、ECS では「複数 Component 型に触る System」であり何も特別でない。
- ADR-0002 のクエリ問題は、REST エンドポイント設計ではなく **System の archetype query** の問題と位置づけ直せる。
- 帰結：**Logos が提供するのは ECS で言う「ワールド」（Entity+Component ストア + クエリ + 変更通知）まで。三位一体はエコシステム全体スケールで初めて完成する。** Logos 単体に完結性を求めても永遠に物足りない（System ゼロのゲームエンジンを眺めるのと同じ）。

### 3. 設計の分岐：(a) vs (b)
- (a) 各レイヤーが自前 DB を持ち、Logos は参照と書き込みルーティングの層。
- (b) Entity/Component ストアを Logos が持ち、各レイヤーは「Component 型を定義し、ビューとロジックを提供する Interface（=System）」になる。
- **(b) に倒す方針で合意の方向。** (b) だとレイヤー間連携が全て同一 Entity 上の Component 参照になり、同期・echo・並行 Conflict の問題群がほぼ消滅する。外部サービスは (b) の世界で「外部にコピーを持つ特殊な Component」として扱い、reconciliation は外部境界だけに局所化される。
- 注意：ドキュメントの「データは各サービスに分散したまま」という哲学は (a) 寄りだが、あれは外部サービス前提の記述。自前レイヤーに分散を強制する理由はない。

### 4. Conflict / Merge / Split の扱い
- **Conflict は構造的に消える。** echo/正規形/並行判定は全て「独立コピーを後から揃える reconciliation モデル」の産物。(b) では値が世界に一つしかないのでコピーがなく、衝突もない。残るのは普通の DB 同時更新（トランザクション/楽観ロックで解決可能）だけ。`sync_and_conflict.md` は無駄にならず、適用先が「コア」から「外部境界」に移るだけ。
- **Merge/Split は内部でも原理的に起きうる**（別の日に Velt ノートと Rotax タスクを作り後で同一概念と気づく等）が、頻度・深刻さが桁違いに低い。型の一意性制約で衝突するのは同型ペアのみ、単独ユーザーなら並行編集窓も極小。→ **精密な設計は実際に困る日まで遅延してよい。**

### 5. 「根底を綺麗にしすぎる癖」への対処
- ユーザーは自認する悪癖として「根底を先に完璧にしようとする」傾向あり。これが「何もわからない」状態の半分の原因。
- **健全な順序：Logos を先に完成させない。** 最初の Logos は「Entity テーブル / Component テーブル / 型ごとスキーマ / 変更通知」程度の薄さ。Merge/Split/外部 Adapter/Conflict 処理は必要になった日まで存在しなくてよい。
- System（レイヤー）側から要求が来て初めて、クエリ API・スキーマ宣言・通知粒度が決まる。System ゼロでそれらを決めるのは原理的に不可能だった。

## 今かけておくべき「安い保険」（2つだけ）
1. **Component の書き込みは必ず Logos の単一の口を通す**（レイヤーが裏口で直接 DB を触らない）。後からロック/所有権/Bridge をその口に差し込むだけで導入できる。
2. **Component への変更を append-only ログ（由来付き）として残す。** Split の本当の困難は「統合期間中の変更の由来不明」だったので、由来付き履歴があれば Split は後日いつでも実装可能な遅延機能になる。**このログは構想中の Yatra（活動履歴レイヤー）とほぼ同一** — 保険ではなく、どのみち作るレイヤーの土台が一つ早く手に入るだけ。

## 次のアクション（推奨）
**Rotax か Velt のどちらか一つを、最小の System として Logos の上に書いてみる。**
- Rotax（タスク・時間レイヤー）の方が形が単純そう。
- Velt（知識・意味・関係レイヤー）の方が思想的に Logos に近い。
- ユーザーはまだどちらから着手するか未決定。次セッションはここから始めるとよい。

## 未解決・次セッションで詰めるべき論点
- (a)/(b) の最終確定（方向は (b) だが明示合意は未取得）。
- Logos コアの最小 API 形（Entity/Component ストア、archetype query、変更通知の粒度）。これは最初の System を書きながら決まる。
- 各レイヤー（Wayline/Zestium/Rotax/Yatra/Velt）が定義する Component 型の初期スケッチ。
- Yatra と「変更ログ」をどう一体設計するか。

## このセッションのユーザーの状態（トーン）
設計の汚さと意義に悩んで一時「何もわからない」状態になっていたが、対話を通じて「Logos = ワールド、レイヤー = System」という整理に納得し、前に進める見通しが立った段階。根底を磨きすぎる癖を自認しているので、次セッションでも「先に作りすぎない／最初の System から引っ張る」方針を支えるとよい。
